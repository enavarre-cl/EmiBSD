# Roadmap

OpenBSD `sys/` is thousands of C files. Even the core (`kern` + `uvm` + `sys` + `libkern` + two
arch directories + a handful of drivers) is several hundred thousand lines. M0 to M6 is realistically a
12 to 24 month hobby arc; the full kernel is multi-year with no fixed end. This roadmap exists so
that progress is **measurable** (`cargo xtask ports status`, `just smoke`), not to promise dates.

Every milestone has a mechanical exit criterion: a command that passes or a serial line that appears.
Editing a milestone must keep that property.

## What "complete" means (proposed 2026-10-03; left open by the user until M13)

"Complete" is every file of `reference/openbsd-src/sys/` that can be exercised in QEMU on amd64 and
arm64, plus what M14 adds for the machines the user names. Out of scope for good, by existing rules:

- Drivers for hardware QEMU does not expose: `status = "skipped"`, `notes = "deferred-driver"`
  (`.claude/rules/scope-and-stubs.md`). They return only through M15, for the named machines.
- `sys/dev/pci/drm/`: code imported from Linux (4204 files at the pin; 128 name the GPL, most of
  the rest are MIT). QEMU's display is served by `efifb`/`virtio-gpu` without it, and the GPL
  files cannot be ported, so the directory is reviewed file by file and expected to land as
  `skipped: license` or `deferred-driver`.
- Anything OpenBSD does not have: containers, namespaces, cgroups, overlay file systems. OpenBSD's
  answer is `vmm(4)` plus `pledge`/`unveil`/`chroot`; adding a Linux primitive would be a design
  deviation, the user's decision, recorded in `docs/ARCHITECTURE.md`, not here.

With this definition the tracker's 100% (`cargo xtask ports status`) is a reachable number.

The user left this section open on 2026-10-03, leaning towards porting everything, drivers
included (drivers are where buffer bugs live, and Rust helps there). What stays out is set by
licence and verification, not difficulty: `dev/pci/drm/` cannot be ported without inheriting
the GPL, and a driver for hardware QEMU does not emulate cannot be tested without the device.
Every `dev/` driver QEMU emulates is in already (M12, M13). The section is closed at M13.

## Order after M8 (decided 2026-10-03)

Security, file systems, SMP, devices and the storage/firmware/console block come before the
product-finishing milestones because every one of them is testable in QEMU 11.1 on the
development Mac and none needs an installer. M14 (installable) stays before M15 (real hardware)
because M15's criterion starts from the M14 ISO. M15 is the only optional milestone, so it is
last: without a named board and PC the project ends at M14, an installable OpenBSD in QEMU,
with nothing half done. `sshd` is userland of M8+ (libc, libcrypto, `/dev/random`, `login`) and
does not wait for M14. The order of work: M7a part 3, then M7+ starting with the network
(M7b, the ping), then M8. The user decided the order on 2026-10-03; what is still open is in
`docs/STATUS.md`.
